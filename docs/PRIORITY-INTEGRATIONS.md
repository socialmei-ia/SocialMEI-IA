## Divulgação

O editor nativo e mídia local são preservados. O painel acrescenta tema, objetivo, oferta/serviço e tom, alternativas editáveis de legenda, solicitação de imagem com erro explícito quando indisponível, revisão e fila compartilhada de preparação simulada.

A migration015 adiciona jobs/eventos sem editar001–014. A API `/api/v1/content/preparation` é opt-in `SOCIALMEI_CONTENT_PREPARATION_MODE=simulation`; a UI exige `contentPreparation:{mode:'simulation'}` e sessão remota. Ausência/valor inválido não habilita operação. Contas são fictícias por workspace, mídia é somente metadado (arquivo não sobe nem persiste); nenhum estado é publicação real. Não usar a fila como backup do arquivo local.

Estados: draft, pending_review, scheduled, processing, simulated, failed, uncertain e cancelled. CAS protege edição/cancelamento; a chave idempotente identifica uma preparação. Workers usam claim/lease e `SKIP LOCKED`; a recuperação após reinício é permitida somente porque o adaptador não tem efeitos externos. Resultados incertos não são repetidos automaticamente. Uma implementação real precisará reconciliação externa antes de qualquer retry.

O comando explícito `python python-service/content_preparation.py --workspace ID --once` processa somente simulações já vencidas em banco descartável habilitado. O botão da interface faz o mesmo para o workspace da sessão. Não existe daemon instalado, tarefa cron ou integração n8n ativa. Agendamentos permanecem no banco após reinício, mas exigem worker de teste explícito; não prometem publicação autônoma.

## Recepção controlada e Caixa

`SOCIALMEI_CHANNEL_INGRESS_MODE=fixture`, chave de teste própria com pelo menos32 caracteres, autenticação/compartilhamento válidos e laboratório de enriquecimento `stub` são necessários. O padrão é disabled. Nenhuma credencial de n8n/WAHA é reutilizada.

- `GET/POST /api/v1/channel-lab/accounts`: registro de instância/sessão `fixture-*` no schema009, sempre inativo e sem envio. Só owner/admin cadastram; sessão, Origin, CSRF e papéis existentes são preservados.
- `POST /internal/channel-ingress/waha`: envelope próprio inspirado em WAHA, **não webhook nativo homologado**. schema_version1, event_id UUID, timestamp UTC em segundos, instance/session cadastrados, event=message, payload com id/from/fromMe=false/type=chat/body/notifyName e signature HMAC-SHA256 do JSON canônico sem signature. Texto limitado, corpo total16KiB, sem campos livres de workspace, JSON duplicado, mídia/saída ou URL externa. Assinatura e janela±120s verificadas antes de abrir o banco.
- Workspace é resolvido pelo registro persistido de conta, não por nome/identidade enviada pelo navegador. Contato usa hash do ID externo; nomes não mesclam contatos. Mensagens e deduplicação reutilizam o laboratório014 e a mesma função transacional da entrada sintética. O horário armazenado é o de recepção; timestamp original do provedor não é afirmado.
- Repetição idêntica devolve o registro existente; troca de conteúdo com ID já utilizado conflita409. Concorrência é serializada por workspace, com quota. Nenhuma escrita ocorre em `crm_mensagens_canal` operacional e nenhum endpoint de envio foi criado.

Após recepção, **Caixa Unificada → laboratório de análise → Atualizar** apresenta as conversas usando o componente existente. A mesma API permite enriquecer, consultar fontes lexicais do próprio MEI e aprovar uma resposta como rascunho, nunca enviar. Duas sessões autenticadas podem ler os registros do negócio. O namespace interno continua fora do gateway público e não deve ser exposto para conectar um fornecedor.
