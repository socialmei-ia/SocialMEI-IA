# Isolated message enrichment adapter

The implementation provides a deterministic synthetic stub, not an installed n8n hook, live connector, language model or send service. `POST /internal/message-enrichment/results` is an optional stub-only internal HTTP callback, authenticated solely by the server-only HMAC envelope. It is not an installed n8n hook. Existing human API routes retain their session/Origin/CSRF checks. The team gateway does not proxy this internal namespace; no gateway, Compose or workflow change is included. `process_event(connection, signed_event)` runs inside a database savepoint. It resolves workspace from the persisted opaque job ID; payload workspace/user/account fields are forbidden.

`SOCIALMEI_MESSAGE_ENRICHMENT_MODE` defaults to `disabled`; only `stub` enables the subsystem. The isolated server key `SOCIALMEI_MESSAGE_ENRICHMENT_TEST_KEY` must have at least 32 characters. It is never exposed through capabilities, responses, frontend configuration or logs and never reuses an n8n key. Existing authentication remains required, including for capabilities. Invalid configuration, missing migration 014 or database failures fail closed with sanitized errors. All responses use no-store.

Signing uses HMAC-SHA256 over canonical sorted compact JSON containing schema_version, job_id, event_id, timestamp, attempt and the SHA256 of the canonical payload. Verification uses constant-time comparison; timestamps outside ±120 seconds fail. The persisted job expires after five minutes. Three attempts are the hard limit; retries require the exact job revision, a still-current message revision and an unreviewed pending/timeout job. Every retry increments attempt and revision and resets the five-minute deadline. Older attempts and superseded jobs cannot apply results. Successful events persist a unique event UUID and full-envelope hash. An exact event replay returns current persisted state, including any later human review; it never rewrites that decision. Changed event reuse conflicts. Results arriving after review, source invalidation, timeout or a newer analysis are rejected. The HTTP route bounds the raw streamed body to 32 KiB before parsing, rejects duplicate JSON fields and query selectors, and verifies schema, canonical HMAC and time before opening the database. Malformed/oversized bodies return sanitized 422, bad signatures 403, expired envelopes 409, disabled/missing-key configuration 503 and unsupported methods 405; responses use no-store. Database work then runs in the worker thread pool.

All public state derives from the authenticated server workspace. GET capabilities/conversations/documents include server-derived `workspace_id` response metadata so the browser can reject shared-cookie/session races; request workspace selectors remain forbidden. Owners/admins manage documents. Members may add synthetic messages, request analysis and review drafts; viewers only read. Conversation identity is workspace + channel + synthetic account reference + external contact reference. Both references must match `synthetic:[A-Za-z0-9_.:-]{1,100}`. Contact names do not establish identity. IDs exposed to the native Inbox are safe integer conversation/message IDs; jobs use UUIDs. The message revision increases per new job, while each job has a separate revision for human review. A newer job supersedes older unreviewed jobs. Approved reviews retain drafts only; rejected reviews permit an empty draft. There is no sending path.

Message operation keys and external-message keys persist deduplication. Exact operation replay does not increment conversation revisions or consume the rate quota. External message IDs are unique per workspace, channel and synthetic account, independent of contact. An identical external-message replay with a new operation UUID persists an alias and consumes the rate quota; changed contact or content conflicts before creating a conversation. Reusing either key with changed normalized content conflicts. Enrichment operations also bind the message path and reload the current job on replay, so cached results cannot resurrect source-dependent suggestions. Transactions lock only the current workspace before quota, dedup and CAS mutations. The aggregate limit is 60 new messages/jobs/documents/retries/accepted callbacks per workspace per minute, with exact operation replays exempt and newly persisted operation aliases charged. Conversation and history reads are bounded to 100 conversations, 100 messages per conversation and 100 history jobs.

Plain-text documents accept at most 32 KiB of UTF-8 content and 120-character titles. Messages, result explanations and suggested drafts accept at most 8 KiB each. Signed envelopes are additionally capped at 32 KiB total. Unknown fields, noncanonical UUIDs, bool-as-integer revisions, unsafe control characters, unpaired Unicode surrogates and invalid channels fail validation. No URL or file retrieval, binary parsing, embeddings or external socket transport is implemented.

There are at most 50 active documents per business, with server-assigned 30-day expiry. Retrieval always filters workspace, deletion and expiry before a bounded lexical match; text only influences matching and is never executed or interpreted as authority or instructions. The synthetic reply does not copy document content. Reads and analysis invoke retention cleanup: expired content is physically cleared, document revision increments and dependent job results are cleared. A pending job deadline is persisted as expired on reads. Explicit deletion clears content immediately and invalidates dependent results within the transaction. Expired sources produce `expired`, removed sources `invalidated`; both return empty suggested_reply/citations, including GET conversations, history and idempotent enrich replay. No background retention scheduler is installed; an isolated caller can invoke the same cleanup function when future scheduling is authorized. Expired content is excluded even before cleanup.

Focused tests use TestClient and a strictly disposable PostgreSQL database via `TEST_DATABASE_URL`. They apply migrations and truncate test data; never point them at a real team database. The fixture for this task uses an internal Docker network and a loopback-only HTTPS gateway. Test-only credentials stay in a private temporary file. All production integrations, migrations, workflow binding and release steps remain outside this implementation.
